# 项目规范与完成标准

本文规范仓库维护；[模板规范](template-spec.zh-CN.md)定义模板契约，
[文档规范](documentation-standards.zh-CN.md)定义文档与示例要求。[English](project-standards.md)。
实验实现、代码合并和提供方部署验证是三个独立状态。

## 所有权与权威来源

| 内容 | 权威来源 |
| --- | --- |
| 模板实现 | 根目录下对应模板的 manifest、Dockerfile 和命名命令 |
| 公共目录 | `awesome-templates.yaml`，每个可安装模板一条 |
| SDK/server 与 CLI 契约 | 对应独立仓库的实际源码、帮助及验收记录的精确提交 |
| 验收 | 模板本地凭证式测试记录及 `.agents/` 工程摘要 |
| 需求进度 | GitHub Issues；历史市场调研不是实现进度 |
| 目录网站 | 独立 registry 仓库 |

修改前阅读 AGENTS、贡献指南、模板专属指令和设计；先检查现有 diff，重叠工作使用
独立分支或 worktree。跨仓库使用完整 GitHub URL，不依赖兄弟目录，不复制网站产物，
模板仓库不代替 SDK/CLI 定义公共契约。

## 设计与实现

每个模板在 `docs/design/<name>.md` 写明用户任务、固定上游来源及许可证、命令 schema、
资源、Express 可行性和可执行测试计划。区分完整产品和真实可运行切片。远程服务客户端
不能证明服务本身在 Express 内运行；硬件、账号、许可、数据集和外部服务限制需明确。
不能用名字相近的程序代替原产品。

从 `_skeleton/` 开始，默认 Express 构建文件保留平台基础镜像、generation、启动与就绪命令、非 root 运行用户、
保留端口和 server SDK 契约；声明提供的服务与显式工作流所需操作。独立构建方案遵循[显式方案规则](workflows.zh-CN.md#显式构建方案)，保留原构建文件。验证参数，限制输入、输出、
运行时间和进程数量；用户输入通过 argv 传递。非零退出必须作为错误，正常结束、失败及
超时均清理自有后代进程。检查命令不得暗中改变配置。隔离生成的工作区，保留调用者文件、
无关进程和原始测试。

依赖使用精确版本或不可变提交，使用已有 lockfile；上游提供完整性哈希时需核验。
安装和构建命令必须明确，包名不等于包已发布。记录包版本和源码提交；升级时复核架构、
平台、许可证、实际安装版本、参数和受影响的运行测试。

## 代码约定

沿用 Python 四空格、清晰 snake_case、明确公共参数/类型及 JSON 可序列化结果。
导入时不得启动 server 或改动云端资源。分开参数验证、上游执行和产物验证；仅在
可恢复或需稳定脱敏错误契约处捕获异常，不能把执行失败变成成功字符串。模板不依赖
兄弟目录。沿用现有工具；引入 formatter/linter 须独立说明范围，不重排无关文件。

## 兼容性与版本

运行行为、依赖、默认值、参数或资源改变时更新模板版本。命令删除、重命名、验证收紧和
权限变化需要同步双语说明；不兼容变化提供迁移方法。manifest、目录、命令表、设计和示例
保持一致。旧版本的提供方证据不能认证新版本，必须作为历史保留。

## 安全、许可证与资源

保留 LICENSE、NOTICE 和上游归属；设计和 README 说明再分发源码、资产、模型和数据的
许可证，没有再分发权的内容不得包含。将输入和 agent 生成代码视为不可信；权限绕过只能
是显式且有文档的选项。

manifest 只声明空值 secret 名称，通过进程环境注入。不得提交 `.env`、凭据、私有 URL、
资源标识、原始提供方或模型日志。不得向其他提供方发送 Express key。云端测试所需调用
在任务授权范围内；将凭据复制到 Actions 或新服务需要单独授权。漏洞通过仓库启用的
GitHub 私密报告功能提交；若不可用，用不含敏感信息的 Issue 索取私密联系方式。

创建云端资源前记录唯一所有权；不确定响应必须通过精确别名和 ID 对账。删除后独立读回
验证资源不存在。清理失败或不确定不能通过。仅删除本次创建资源，说明 TTL、取消限制、
保留策略和尚需处理的私有恢复记录。

## 验证与证据

运行受影响的检查和所有适用 CI 门槛，具体命令以 workflow 为准。复用回归套件，行为
缺陷必须增加修复前失败、修复后通过的回归。mock 只证明控制器行为。

| 变化 | 必要验证 |
| --- | --- |
| 文档 | 本地链接、示例、翻译、工程记录、diff |
| 规范、检查器、目录 | `python scripts/test_spec_tools.py`、`python scripts/check_template.py --all` 和针对性回归 |
| 运行逻辑、依赖 | 单元及进程测试、L0；镜像变化补镜像构建及版本检查 |
| 提供方声明 | 精确版本的真实部署、外部 CLI/SDK smoke、独立清理确认 |
| 编码或模型声明 | 真实模型修改已有源码、新建产物、保留原测试、独立隐藏断言 |

L0–L4 定义沿用模板规范。step 验收记录构建方式，不能声称构建过 Dockerfile；源码运行
不能代替镜像部署。缺 key 和 SKIP 明确保留。每个修改仓库都有英文七节决策记录及带日期
证据，放在自己的 `.agents/` 并链接模板原始记录。证据包含 PASS/PARTIAL/FAIL/BLOCKED、
精确范围与哈希、工具版本、实际命令、数量、限制和清理。历史合并证据不可覆盖。

## Issue、评审与交付

复用对应 Issue，逐条核对验收条件，区分复现缺陷和假设。较大需求分别跟踪设计、实现、
本地、镜像、Express、模型、文档和合并状态。Issue 若要求真实部署，仅新增目录或合并
experimental PR 不足以关闭。只有 Issue 明确接受可行性决策且证据完整时，才能以此关闭。
外部阻塞和缺少输入保持可见。

使用 Conventional Commits、仓库 PR 模板，说明行为、测试和实质限制并关联 Issue。
推送任务分支，检查最新 head 的 CI 和评审；全部适用门槛通过后用允许方式合并。
不得绕过保护、强推共享历史或直接推主分支。读回确认 MERGED、Issue 条件和合并后检查。

目录资格、包发布和合并是独立过程。不得臆造 tag、包版本或 registry 发布状态。
release/tag 操作须有授权范围、兼容说明和验证产物；示例安装引用必须指向真实已发布
提交或 tag。

## 完成标准

- 请求行为与全部验收条件实现，或交付 Issue 明确接受的、有证据的可行性决策。
- 模板、目录、双语文档、设计、契约版本一致。
- 必要回归与最新 CI 通过；必要真实 Express/模型测试有精确来源及独立清理证明。
- 许可证和归属保留，范围 diff 和配置 secret 扫描通过。
- 工程记录及索引完整，失败和跳过明确保留。
- PR 实际合并；Issue 仅在全部条件交付后关闭。

缺少任一必要条件时报告具体前置条件和已完成产物，不能将部分实现描述为完成。

pip哈希锁安装使用--require-hashes -r与一个显式COPY的本地锁文件。每项依赖必须固定精确版本和SHA256，不混入额外未固定包、外部requirements或索引指令。检查器支持简单COPY源到目标文件映射；镜像内仍需pip实际哈希校验及pip check。


需要新版服务器契约时，模板可增加 `server-sdk.commit`：单个小写40位公开 commit
加换行，必须与 Dockerfile 的不可变服务器 fallback 一致。L1 先检出该源码构建
wheel，归档及注册证明核对相同 pin；该文件计入上下文哈希。没有该文件的模板
继续使用历史共同注入 pin，增加一个消费者不会更改或重新认证其他运行时。

默认 Dockerfile 中的服务器归档提交必须与 `scripts/server_sdk_pin.py`（或显式的 `server-sdk.commit`）一致。检查器拒绝不一致的 fallback，确保默认构建与 CI 注入构建选择同一服务器源码。修改提交后须重新完成对应源码的镜像及工作流验收，原有回执仅作为历史保留。
